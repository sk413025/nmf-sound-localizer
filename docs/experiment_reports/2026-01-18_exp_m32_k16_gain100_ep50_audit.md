## Data leakage risks (design-level)
### A) Train/val split leakage is likely (sequence-level split)
- The training script constructs a sequence dataset and applies `torch.utils.data.random_split`.
- The dataset is flattened into **one sample per frequency per time-window block**. A random split at this flat-sample level will almost certainly place samples from the *same underlying time-window block* into both train and val (train/val contamination within-block).

Impact:
- Validation loss/accuracy can appear much better than true generalization to unseen clips.

Status:
- **Likely present by construction**.
- The current saved trajectory blocks **do not contain clip identifiers**, so we cannot quantify the overlap precisely for this particular run.

### B) Evaluation is not a held-out generalization test
- Evaluation uses the same dataset roots as trajectory generation and (indirectly) training.

Impact:
- DT≈OMP at K=16 should be interpreted as **in-distribution imitation** performance, not out-of-distribution generalization.

### C) RTG is lookahead/non-causal (only a problem for streaming deployments)
- In evaluation, RTG is computed from residual energy over the observed LDV STFT window $Y$.

Impact:
- If $Y$ is available at inference (offline reconstruction / windowed processing), RTG is not leakage.
- If deployment is streaming and disallows access to the full Tw-block, RTG is a lookahead feature and will overestimate deployable performance.

## Bug/over-optimism risks (implementation-level)
### 1) “Perfect” capture at K=16 can be mathematically expected
- With Tw=16 and K=16, per-frequency least squares has enough degrees of freedom to closely interpolate a length-16 target window if the dictionary columns are not degenerate.
- Therefore, high capture at K=16 is not automatically evidence of leakage.

### 2) Soft-metric epsilon-floor artifact is controlled
- This run uses Gain=100 in generation and evaluation.
- That prevents energies near 1e−8 from being dominated by the 1e−6 denominator epsilon.

### 3) DT > OMP at small K is plausible
- OMP is greedy w.r.t. its own residual and correlation criterion.
- DT is trained to choose actions that improve the capture objective; it may choose atoms that improve early-step capture better than OMP’s greedy path.

## Recommendations (to make leakage checks conclusive)
1. Add clip/window identifiers to each saved trajectory block.
2. Enforce and log clip-level splits (train/val/test) with explicit manifests.
3. Add a held-out evaluation set (unseen clips or angles).
4. Replace oracle RTG with a deployable proxy if deployment realism is required.

## Conclusion
The run is reproducible and does not show trivial duplication. However, results are plausibly optimistic because (1) evaluation is in-distribution, (2) validation likely mixes highly correlated sequences across train/val, and (3) DT uses an oracle RTG feature derived from the target.
